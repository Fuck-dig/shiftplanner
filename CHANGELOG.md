# Changelog

Everything completed, newest first, with the reasoning behind it. Split out of
`TASKS.md` once the finished work was 92% of that file — the to-do list should
be what's left, not a filing cabinet.

Severities are the ones assigned at the time: how worried to be if the item had
been left alone.


## 2026-08-07

- **Creating a restaurant is now a setup step, not just a name box (requested)** - it asked for a name and a currency; everything else was a column default you discovered months later in Costs, if at all. Two of those defaults quietly shape money: sick pay decides what a sick day costs, and the pay period start decides which month a shift is paid in. Both are now asked once, at the point the restaurant is created, so they are a decision rather than something inherited. Pre-filled with the common answer (100% sick pay, 16th) so pressing Create without touching them is still a valid path, and the form says in a line what the period will actually run. The pay-period field is capped at 1-28 in the UI as well as in the CHECK constraint, because the 29th to 31st do not exist in every month and a period anchored there would fail to open in February. The save is still deliberately best-effort: a failure writing settings must not strand someone outside a restaurant that HAS been created, and every value has a working column default, so the worst case is defaults rather than a broken restaurant.

- **"Role" meant two different things, and Profile was the odd one out (requested)** - Rorota has membership roles (owner / manager / employee, i.e. what you can DO in the app) and job roles (Waiter, Bartender, Kitchen, i.e. what you can be SCHEDULED as). Everywhere except Profile, "role" means the second: shift roles, role colours, Cost by role, the badges on every grid, the drag-to-reorder legend. Profile alone showed "Role: Owner". The sharpest part is that **Manager is both**, so the same word on the same screen could mean either. Profile now shows **Access** (what you can do here) and **Roles** (what you can be scheduled as, as the same badges used everywhere else), each with a one-line explanation. Nothing is hidden - the access level still matters, because it explains why someone sees what they see - it just no longer borrows a word that means something else. Dead `profile.role` key removed from all five languages.

- **Your pay terms in your own Profile (requested)** - a read-only card showing your rate (hourly or monthly), your sick pay percentage and whether it is the restaurant default or set for you, and your weekly max. Salaried staff also see the derived hourly equivalent, which is what their shifts are actually costed at - that number explains why the pay card's arithmetic looks the way it does, and hourly staff are spared it because they would just see their own figure twice. Absent entirely when no wage has been entered, rather than a row of zeroes that reads as a claim about what somebody earns. Deliberately separate from the pay CARD on the schedule: this is the terms, that is what the terms come to this period.

- **A custom-hours open shift could be filed under a service it did not run in (severity 4/10)** - William's 18:00-22:00 waiter shift sat in the Lunch row under a heading reading 10:00-16:00. Fixed by choosing the block FIRST and fencing the hours to it: `withinWindow()` in dates.js backs new `min`/`max` props on TimePicker, so picking Lunch greys out 18:00 in both the dropdown and the typed field. Handles services ending at midnight and services crossing it. Custom hours are for trimming a service, not for inventing one that spans two.

  Four attempts, and the first three are the lesson. Hardcoded to blocks[0]; then a free picker, which let you create the same contradiction deliberately; then derived from the start time, which was self-consistent but moved the service under you as you typed and left the block un-choosable. Each fix addressed the symptom William had just described rather than the shape of the thing - the state was reachable, so it kept being reached. Constraining the input is what finally removed it. `blockForTime()` and its nine tests were deleted in the same commit: an exported helper implying a rule the app no longer follows is worse than no helper.

### Cleanup pass 1 — dead code and drift (13 Aug)

Now `PeriodNav`, with the three-way branch extracted further into `lib/period.js` (`periodUnit`, `stepMonth`) so it is finally testable: 6 new tests, all three mutations caught.

The reasoning in the comments was kept where it explains the code rather than the suppression; one comment read "the two eslint-disables below" above three of them, which is how stale it was. `lint:ci` now reports zero errors AND zero warnings for the first time.

- **Two lib functions passed to TeamView as props** - Dashboard imported `assignmentHours` and `actualAssignmentHours` and handed them down, while TeamView already imported six other helpers from the same module. TeamView now imports its own; `assignmentHours` turned out to be passed but never used at all.

- **`swapTimes` tests living in `sickPay.test.js`** - moved to `openShift.test.js`. A test file named after one feature and containing another is how you end up deleting the wrong thing.

- **The open-shift dialog was taller than the screen (severity 2/10)** - it rendered one row per block, each with its own Add button, so the custom-hours option sat below the fold and you were asked to commit before you had seen it. Now four short choices - day, role, service, hours - and ONE action, in the footer beside Cancel where the other actions already were. "Whole service" and "Custom" are a two-way toggle over the same state (no stored times IS "whole service"), so they cannot disagree; a shift left on the whole service still follows the block if its hours are edited later.

- **"Add" and "Done" on a dialog that was updating an existing shift (severity 2/10)** - the open-shift dialog does double duty for posting and editing, and only the title changed. Now the action reads Update and the escape hatch reads Cancel when editing.

- **Posting an open shift inherited the role from the last shift EDITED (severity 3/10)** - `openShiftRole` was one piece of state doing two jobs, so opening an "Other" shift to look at it made "Other" the default for the next thing posted. The posting default now lives in its own ref, updated only when a role is picked for a new shift. Stickiness between posts is wanted; inheriting from an edit is not.

- **An open shift's hours were shown as the BLOCK's in three separate places (severity 5/10)** - the one that matters most: the staff "Open shifts" row displayed a shift posted for 18:00-22:00 as "Lunch 10:00-16:00", so somebody could take a four-hour shift believing it was six and find out on the day. Cause is the same everywhere: each render site independently reached for `block.start`/`block.end`, which was correct until open shifts could carry their own hours and silently wrong afterwards. Fixed in `swapWhen` first, then the Week grid, then the Team chip - and the staff row was missed TWICE before William's screenshot caught it. So it is now one exported helper, `swapTimes(sw, block)`, used by all four sites and covered by tests, rather than a rule everyone is expected to remember.

- **The custom-hours open shift silently attached to the wrong block (severity 5/10)** - found by William running test B3, the round trip nobody had ever executed. Posting "Waiter, 18:00-22:00" created an open shift on LUNCH, because the Custom row hardcoded `blocks[0]` with no way to choose. So the shift existed, with the right times, filed under a block nobody would look at - and as a bonus, `openToAnyone` correctly hides an open shift on a block you already work, so the test staff member couldn't see it either. Two independent reasons for "it doesn't show up", one of them mine. The Custom row now asks which block, because an open shift genuinely belongs to one (coverage and claiming are keyed on it) and the honest answer to an ambiguous choice is to ask rather than guess. The add-a-shift modal has the same `blocks[0]` shortcut and is worth the same treatment - noted in TASKS.

- **Open shifts can be edited, not only deleted (requested)** - clicking a posted open shift reopens the same dialog pre-filled, so "I meant Dinner" is a correction rather than a delete-and-repost. Editing UPDATES the row instead of creating a second one, which is the mistake that would quietly double your open shifts every time somebody fixed a typo. Only while the shift is still `open`: once claimed, the chip is inert and says why, because changing the hours under someone who already accepted them is changing a deal after the fact. `updateShiftSwap` gained block/role/day/times, each guarded by `in` so clearing custom times back to "use the block's hours" is expressible rather than indistinguishable from "don't change it".

- **"This month" in Costs was not a month (severity 6/10)** - found by William during the test pass: the same person read 208.5h in Costs and 141h on their own pay card, both labelled August. Costs summed `getMonthOffsets`, which returns six whole WEEKS - for August 2026 that is 27 July to 6 September, 42 days, displayed as "August 2026". Every monthly cost figure was overstated by whatever fell in those eleven extra days. Worse, the labour-cost % divided those 42 days of wages by `monthRevenueTotal`, which was already a strict calendar month: six weeks of wages over one month of sales. Now a real calendar month, so both screens mean the same thing and labour % compares like with like. Expect monthly figures to DROP after this - they were too high, not too low.

- **Fixed by extracting the walk rather than patching both sides** - `collectShiftsInRange` is now the single definition of "this person, these dates", and both the pay card and Costs call it. They cannot drift apart again without somebody deliberately writing a second walk. Two tests pin it: one asserting a calendar month excludes the Monday of the preceding overlapping week, one asserting the two callers agree. Mutation tried (removing the range filter), caught by three.

- **The 7 Aug "labour % looks low" banner is KEPT, and is now actually true** - I nearly deleted it as wrong-headed. Checking properly: it describes the case where some weeks in the month have no schedule, and in that case labour genuinely covers fewer days than revenue, so the percentage does read low. What I had missed on 7 Aug was a SECOND, opposite effect sitting on top of it - the six-week span overcounting labour - which could mask or invert the very thing the banner warned about. With months now being months, the banner means exactly what it says. Worth recording that my first instinct here was to "correct" something that was right; the difference was checking which of two effects the sentence was about.

- **Staff can see what they're due (requested)** - a "Your pay" card on the staff schedule, switchable between the pay period, a calendar month and the current week, with arrows to step back through previous ones. Shows expected pay, hours, sick pay when there is any, and a line per shift. It runs the SAME arithmetic as the manager's Costs tab, reusing the same helpers rather than reimplementing them - actual clocked hours falling back to the schedule, a no-show counting zero, sick shifts at whatever percentage applies, monthly salaries converted to an hourly equivalent. If the two ever disagreed, one of them would be lying to somebody about their money. It therefore follows reality as it changes, which is what was asked for: punch out early and it drops, pick up a shift and it rises, get marked sick and it pays at the sick rate. Upcoming shifts are included and counted at their scheduled hours, with the card saying how many of those hours have not been worked yet, so the estimate is labelled rather than implied. 32 tests across the two new modules; three mutations tried against the date logic, all caught.

- **Pay periods: 16th to 15th, paid the last banking day of the month the period ENDS in** - so 16 Jun-15 Jul pays at the end of July, not August. There is a test pinning that specific off-by-one because it is the one a future reader is most likely to "correct". Boundaries are inclusive at both ends: the 15th is the last day of its period, not the first of the next. The start day is an org setting (`pay_period_start_day`, default 16, constrained 1-28 because 29/30/31 do not exist in every month) rather than a constant, since it is a restaurant-level agreement. Payday is NOT holiday-aware - it steps back off weekends only. Danish public holidays move with Easter and vary by agreement, so a hardcoded list would be wrong somewhere and stale eventually; being a day out beats confidently showing a wrong date, and the card says "expected", not "payslip".

- **Migration `20260811140000`: one narrow hole in the wages table** - `employee_wages` was manager-only on all four operations, deliberately, because it holds what everyone earns. Staff now get exactly one SELECT policy, scoped by the existing `my_employee_id(org_id)` helper, so a person reads their own row and cannot reach a colleague's. Insert, update and delete stay manager-only: you can see your pay, you cannot set it. Permissive policies are OR'd, so this sits alongside the manager policy rather than replacing it - verified live before building the UI, and the migration's own check query reports "SCOPED TO EVERYONE" in red if anyone ever widens it. The standing rule this creates: a column belongs in `employee_wages` only if the person it describes may see it.

- **The deploy gate was not checking what the README said it checked (severity 6/10)** - `lint:ci` enabled exactly one rule, `react-hooks/rules-of-hooks`. README describes it as the "hooks + undefined-identifier gate" and says `vite build` is not verification precisely because "it does not check for undefined identifiers". Neither did the gate. Found by falling through it: a `LOCALE` used but never imported in KioskView sailed past lint, tests and build, and would have thrown a ReferenceError the moment the kiosk header rendered. `no-undef` is now on - squarely inside that config's own stated remit, "this breaks at runtime for users" rather than style.

Introduced twenty minutes earlier by the density-toggle work, passed every gate, and would have crashed the staff day-timeline for anyone who opened it. Fixed by passing it as a prop. Two real runtime errors in one afternoon, both invisible to the previous gate, is the argument for the rule.

- **Staff get the compact/comfortable toggle (severity 4/10, a parity gap William asked for a while back)** - `gridTight` existed in the manager's Dashboard and WeekView only, so staff - the people most likely to be on a phone - were stuck on one density. Now in the staff view too, in the same position, with the same wording and the same behaviour, covering the team grid rows, the avatars, the shift cards and the day timeline. Compact keeps the block name and start time and drops the end time and hours total: enough to recognise a shift, and the rest is one tap away. Persisted per browser, which the manager's version never was - it was plain `useState(false)`, so anyone who preferred compact re-set it on every reload. Both sides now remember.

- **Fixed the same `1fr` auto-minimum bug lurking in the staff grid** - the staff team grid repeated `${isMobile?130:180}px repeat(7,1fr)` inline across four separate grids. That is exactly the fault that put shift cards under the wrong day in the manager's Team view: a `1fr` track cannot be narrower than its content, so a header of short day labels and a body of shift cards compute different column widths from the same string. Nobody had reported it here, but it was the same latent bug waiting for a narrow enough screen. Now one shared definition using `minmax(0,1fr)`, so the four grids cannot drift apart.

- **Open shifts can carry their own hours (requested)** - posting one now uses the full add-a-shift dialog: month calendar, role chips, a row per block, and a Custom row with its own start and end. Previously an open shift was only ever "a whole block in the week you were looking at", while adding a shift to a NAMED person had allowed custom times for ages - the two paths disagreed about what a shift is. Six places had to change, and the last two are the ones that make it real rather than decorative: `approveSwap` now carries the posted hours onto the assignment when someone claims it (without that, the times a manager chose were silently discarded the moment it was taken, and the person would turn up for the whole block), and `swapWhen` - the label staff read when deciding whether to take a shift - shows the shift's own hours rather than the block's. Getting that one wrong would tell somebody they were taking 16:30-00:00 when the shift was 18:00-22:00, and they would find out on the day. `postOpenShift` also takes a week key now: the dialog spans a month, and letting it keep assuming the week on screen is exactly how a shift gets posted into the wrong week.

- **Migration `20260811100000_open_shift_custom_hours.sql`** - two nullable text columns on `shift_swaps`, with a CHECK that they are both set or both null (a half-set pair would force the app to invent the other end from the block, which is the silent guess this feature removes) and a loose format check. NULL means "use the block's hours", which is what every existing row means. Deliberately NOT backfilled with each block's current times: doing so would freeze today's hours into old rows, so editing a block later would stop affecting open shifts posted before the migration.

- **Posting an open shift uses the same dialog as adding a shift (requested)** - in the Team tab "+ Open" opened a cramped ~150px dropdown with every block and every role squeezed into tiny chips, while "Add a shift" two rows below opened a proper centred dialog. Same task, two different shapes. The dropdown was a consequence of WHERE it lived rather than a design choice: inside a cell of a horizontally scrolling grid, so anything wider would have been clipped by the scroll box or covered the neighbouring day. Rendering it through a portal to `document.body` escapes that entirely, so it now reuses the add-shift shell - same overlay, radius, width, spacing and type - with room for readable block names, their hours, and full-size role buttons. One addition the dropdown didn't need: the dialog states which DAY you're posting for, which was obvious when it hung under the column and isn't once it's centred.

- **Generate now asks before destroying a week (severity 5/10)** - Generate REPLACES a week rather than merging into it, so pressing it on a week you had hand-tuned discarded every manual edit, silently. It also never checked `confirmed`, so it would just as happily rewrite a PUBLISHED week that staff are already planning around - with no notification, the shifts simply changed under them. Out of step with the app's own conventions, which confirm before applying a template and before archiving someone. Now both entry points ask, with stronger wording when the week is published, and `generateMonth` - which rewrites every week in the month and is the more dangerous of the two - says how many weeks and how many of them are published. The empty-state Generate buttons are untouched: they only render when there is no schedule, so there is nothing to lose.

- **Three small ones** - Costs' "Staff scheduled - X of N" counted archived people in N, so the denominator grew every time someone left (same family as the Team-view headcount bug); fixed with `activeOnly`, while the ROWS deliberately still show archived people who worked the period. An employee's name was a bare text node in a wrapping flex row, so "Nikolaj Ry" split across two lines while the role badges sat beside it - now one unbreakable item, so the badges wrap instead, which is what should give. And `TESTING-today.md` is folded into `TESTING.md` as section 10: a checklist named after a particular day is actively misleading a week later, and the two sections in it that were never run are the least-verified part of the app, so they belong in the real list.

- **The generator no longer lets role order decide who works (severity 6/10)** - roles are now filled SCARCEST-FIRST rather than in list order. Previously whichever role came first got first pick of anyone qualified for two jobs: with one flexible person and one waiter-only person covering a Waiter+Bartender block, "Waiter first" spent the flexible person waiting tables and left the bar empty, while "Bartender first" filled both - same staff, strictly better rota, decided by list order. And that list is the drag-to-reorder order from the day timeline, which managers were told is a display preference. Sorting by SLACK (candidates minus openings) is independent of the incoming order and spends scarce people where they are scarce: a role with one candidate for one opening settles before one with six candidates for one. Ties break on the original order so results stay deterministic. Four new tests, including one asserting both role orders produce an IDENTICAL rota - not merely an equally full one.

- **A mutation test caught the test suite being too weak** - swapping the rule from "fewest spare candidates" to "fewest candidates" passed all 17 tests, meaning nothing pinned the distinction that the fix rests on. Added a case where the two rules genuinely disagree: 3 candidates for 3 waiter openings (slack 0) against 2 candidates for 1 bartender opening (slack 1), where ordering by candidate count fills 3 slots and ordering by slack fills 4. Now caught. Worth noting the sequence - the implementation was right, the tests were not, and only deliberately breaking the code revealed it.

- **Compact fits the whole week on screen — in TEAM view only (requested, half reverted)** - compact previously just made rows shorter; the grids still enforced a minimum width per day and scrolled sideways. Team now drops that minimum, so seven columns divide the available width and nothing scrolls. It works because Team already pins its columns to equal widths with `minmax(0,1fr)`, and because a compact Team cell is a single ~40px chip - a block letter, a start time and a colour.

- **The same change to WEEK view was wrong and is reverted** - shipped it to both grids on the same reasoning and William's screenshot showed Week badly broken: avatars overlapping each other, "+Add+Add" run together, "Post as" and "Refresh" colliding. The mistake was treating the two grids as equivalent because their column MECHANICS are similar (`tableLayout:'fixed'` versus `minmax(0,1fr)`) while ignoring that their CONTENTS are not remotely equivalent. A Week cell stacks avatar chips plus "+ Add" and "+ Open" per role and needs three or four times the width of a Team cell. Squeezed to ~40px with the minimum removed, there was nowhere left to scroll, so it overlapped instead. The minimum width is what keeps that grid legible. Week on a phone wants FEWER columns - isolate a day - not thinner ones, and there is now a comment on that line saying so, so the same idea doesn't get retried.

- **Mobile toolbar: four rows of controls down to two (severity 3/10, reported as "cramped")** - on a phone the schedule toolbar wrapped into four rows (week nav + Today / view tabs + search / slots + missing + Draft + Confirm / History + Print + Delete), so the rota itself started well below the fold. History, Print and Delete move into the ☰ menu that already exists — occasional actions, one tap further away, nothing removed — and they only appear there when a week is actually open, so the menu never offers to print or delete nothing. The staff search collapses to a magnifier until tapped, and auto-expands whenever a term is already active so a filter can't be running with nothing on screen to show for it. What deliberately stays visible: slots, missing count and Confirm. Those are what you opened the screen to see, and the missing count is the number most worth not burying.

- **Two more things off the edge of a phone screen** - both visible in William's screenshots, neither reported, both unreachable rather than merely ugly. The Employees action row (Add shift / Message / Clone / Edit / Archive / delete) was a flex row with no `flexWrap`, so on a phone the last buttons ran off the right and could not be tapped at all. And Costs used fixed pixel column templates - the employee breakdown is `160px 48px 52px 1fr 80px`, about 380px of fixed width before the bar, which does not fit a 390px phone once card padding is taken off, so the cost figure sat off-screen. Costs now takes the same `isMobile` breakpoint the rest of the app uses and drops the progress bars and the priority % on a phone, keeping name, hours and money. Note for anyone changing these: the CELLS have to be dropped alongside the columns, because a three-column grid with five children silently wraps onto extra rows.

- **Team grid now scrolls exactly like the Week grid, which had solved this already** - William's answer to two failed attempts was "can you just make it the same as in the week view", and he was right: WeekView is one `overflowX:'auto'` box containing a table with `tableLayout:'fixed'`, header inside the same scroller, no stickiness and no JS. Its own code comment describes the identical bug — "a cell sizes to its widest child, so adding a single open shift visibly widened that whole day relative to the others" — meaning the fix existed in this repo the whole time and Team view simply never got it. Team now matches: one scroll box, `minmax(0,1fr)` columns (the CSS-grid equivalent of `tableLayout:fixed`), header as a normal first row that moves with the content by construction. Also dropped the `stickyTop` prop, dead once nothing sticks.

- **Two attempts before that, both worth not repeating** - syncing two scrollers in JS, which always lags on iOS because momentum scrolling runs on the compositor and a scroll handler does not; and a CSS-sticky header inside a self-scrolling box, which is smooth but makes the grid scroll within its own height instead of with the page — a bigger behavioural change than the bug warranted, and on desktop too. The general lesson is the one William supplied: before designing a fix, check whether a sibling screen already solved the same problem.

- **Superseded: JS scroll sync and the self-scrolling sticky header** - the sync worked but visibly lagged on a phone, and William asked whether that was fixable "in a real app". It isn't, not with two scrollers: iOS momentum scrolling runs on the compositor thread while a scroll handler runs a frame or two behind it, so the header always chases the body. Any app syncing two scrollers has this. So the two containers are now one, with the header row `position:sticky; top:0` INSIDE it — sticky is handled by the compositor, so the header cannot drift and there is nothing left to synchronise. All the JS (two refs, a callback, a re-entrancy latch) is gone. The trade, stated because it is real: the grid now scrolls within its own height instead of with the page, which is the standard spreadsheet pattern and the only way to pin a header without JS. Worth checking on desktop as well as phone, since it changes where the scrollbar lives there too.

- **The actual cause of the misaligned Team grid: `1fr` is `minmax(auto,1fr)` (severity 6/10)** - my first fix (syncing the two scrollbars, below) was a patch on the wrong layer, and William's next screenshot showed why: the header columns were ~130px and the body columns ~100px. They weren't scrolled apart, they were DIFFERENT WIDTHS, and no amount of matching scrollLeft can align columns that aren't the same size. Cause: all five grids in TeamView share the template `${nameW}px repeat(7,1fr)`, and a `1fr` track carries an implicit AUTO MINIMUM - it can never be narrower than its content. The header cells hold "Mon / 3 Aug"; the body cells hold shift cards reading "Dinner 16:30-00:00 7.5h". So the body's tracks were pushed wider than the header's by their own contents, from the same template. Fixed with `minmax(0,1fr)`, which drops the auto minimum so all five grids compute identical columns. The scroll sync is still needed - there are genuinely two scroll boxes - but alone it was never going to work.

- **The same auto-minimum was also what made the cards "elongated"** - at 54px per day column on mobile, a card could not fit "16:30-00:00" on one line, so it wrapped into "16:30- / 00:00" and grew tall and thin. It also dragged the whole track wider, which is the misalignment above: one root cause, two symptoms, reported separately. Times and block names are now `nowrap` (names ellipsize) and the mobile day column is 104px, which holds the time on one line with a little slack rather than depending on exact font metrics.

- **The Team grid showed shifts under the wrong day on a phone (severity 6/10)** - reported by William from a real phone as "2 different sliders" and "the cards are not on line", which turned out to be one bug. TeamView renders the sticky day header and the grid body as two separate `overflowX:'auto'` boxes over the SAME column template, with nothing tying their scroll positions together. On a desktop the table fits, nobody ever scrolls either one, and the split is invisible. On a phone it doesn't fit: you swipe the body, the header stays put, and every shift card ends up sitting under the wrong date - a rota that is confidently wrong, which is worse than one that is merely hard to read. Fixed by syncing the two scrollLeft values, with a latch so the programmatic scroll doesn't fire the opposite handler and ping-pong. Kept as two boxes deliberately: merging them would cost the sticky day header.

- **lint:ci earned its keep again** - the first version of that fix put `useRef`/`useCallback` below TeamView's `if(!schedule) return` early exit. Four rules-of-hooks errors, caught before it went anywhere near a branch. That is the exact pattern that white-screened production on 3 August, and `vite build` passes it happily - which is why the gate is three commands and not one.

- **Audited the schedule generator, which had NO tests (severity 6/10 for what it found)** - 84 tests in schedule.test.js and not one of them touched `buildSchedule`, the app's headline feature. 15 characterisation tests added, pinning what it actually does: fills required roles, refuses to exceed maxHours, skips APPROVED leave only (pending requests deliberately don't hide someone), enforces the 11-hour rest minimum, picks the cheaper of two candidates and falls back to priority when nobody has a wage, prefers someone under their target over someone at it even when dearer, adds a manager to a staffed block but never invents one for an empty block, and reports what it couldn't supervise via `noMgr`. Two mutations tried - deleting the under-target spreading rule and the rest check - and both caught.

- **THE FINDING: reordering roles silently changes the rota (severity 6/10)** - `buildSchedule` fills roles greedily in `allRoles` order with no backtracking, so a person who holds two roles is consumed by whichever is considered first. With one flexible person and one waiter-only person covering a Waiter+Bartender block: "Waiter first" fills one slot and leaves the bar empty, "Bartender first" fills both. Same staff, same block, strictly better rota - decided entirely by list order. And `allRoles` is `mergeRoleOrder(roleOrder, …)`, i.e. the drag-to-reorder list from the day timeline, which was built and described as a DISPLAY preference. Nothing anywhere tells you that rearranging it changes who works. Both orders are pinned in tests so the coupling can't be lost again; the fix is a decision (scarcest-role-first, or separate display order from solve order) and is written up in TASKS.md rather than guessed at.

- **Dead code removed from the manager-cover pass** - a branch that searched `assigned` for a "hidden" manager to relabel. Unreachable: the line above it returns early on `.some()` of the same predicate over the same array, so `.find()` was always undefined by the time it ran. Also documented, rather than changed, that the "borrow a manager from another block" fallback beside it almost never fires - any other block the same day is within the 11-hour rest window, so it gets rejected. It looks like a safety net and isn't; the `noMgr` list is what actually tells you a block went unsupervised.
